# Shamba Link — Production Implementation Blueprint

## 1. Product and architecture decisions

Shamba Link connects farmers to crop/livestock diagnostics, verified agricultural experts, and nearby agrovets. The application is a modular monolith initially: one typed Express API and one React SPA, backed by PostgreSQL. This keeps deployment and transactions understandable while leaving clear boundaries for extracting AI processing or notifications later.

### Chosen baseline

| Concern | Choice |
|---|---|
| Web client | React, TypeScript `strict`, Vite, React Router, TanStack Query, Tailwind CSS, Lucide React |
| API | Node.js LTS, Express, TypeScript `strict`, Zod validation |
| Persistence | PostgreSQL 15+, Knex migrations and seeds |
| Authentication | Short-lived signed JWT access token; bcrypt password hashes |
| Media | Multer memory storage with file limits; Cloudinary private/original storage and controlled image delivery |
| AI | Provider-neutral diagnostic adapter, asynchronous-capable job boundary, human-review path |
| Tests | Vitest + React Testing Library on web; Vitest/Jest + Supertest on API; PostgreSQL integration tests |
| Deployment | Static web hosting/CDN, API container, managed PostgreSQL, object/media provider, TLS and centralized logs |

Tailwind is selected rather than combining Tailwind and Materialize: mixing two styling systems increases CSS size and makes responsive behavior harder to standardize. The API contract and UI design should support poor connectivity: small initial bundles, compressed/resized images, pagination, explicit retry states, and no requirement for video.

### High-level request flow

```text
Browser / PWA
  ├── HTTPS JSON and multipart requests ──> Express API
  │                                           ├── JWT/RBAC + Zod validation
  │                                           ├── Knex ──> PostgreSQL
  │                                           ├── Media adapter ──> Cloudinary
  │                                           └── Diagnostic adapter ──> AI provider
  └── signed/controlled media URLs <───────────────┘
```

The API owns authorization and validation; the browser is never trusted for role, price, stock, diagnosis ownership, or order totals. Keep database transactions within the API. External AI/media calls must not be made while holding a database transaction open.

## 2. Relational data model

### Modeling and integrity choices

* UUID primary keys are generated by PostgreSQL with `gen_random_uuid()`. Use PostgreSQL 13+.
* Timestamps are `timestamptz`; persist UTC and convert only for display.
* Native PostgreSQL enums constrain roles and lifecycle states.
* `ON DELETE RESTRICT` protects transaction and diagnostic history. Deactivation/soft deletion should be added if account-retention policy requires it; do not hard-delete an account with linked records.
* `order_items.price` is an immutable purchase-time snapshot. `products.price` is the current catalog price.
* An order belongs to one vendor, matching the requested schema. The API rejects a cart containing products from multiple vendors; the client groups cart lines by vendor before checkout.
* Product/order quantities and monetary values have database checks in addition to request validation.
* `diagnoses.farmer_id` is the owner of the uploaded diagnostic. `consultations` must be checked in the service so its farmer matches the linked diagnosis.
* A consultation’s expert must have role `expert`; a product/order vendor must have role `agrovet`; a farmer must have role `farmer`. These cross-row role conditions are enforced in services (ordinary foreign keys cannot enforce another row’s enum value).
* Administrators are provisioned through the explicit bootstrap command, never public registration or demo seeds. Their overview is read-only except for authorized payment receipt review.

### Seed policy

Seed only deterministic, non-sensitive development/test fixtures. Hash fixture passwords with the same bcrypt helper used in registration; never seed production accounts or real personal data. Make seeds idempotent using stable fixture emails and `onConflict("email").merge(...)`. Include one farmer, one agrovet, one expert, several products, and one sample diagnosis only in non-production environments. Provision administrators separately using the explicit bootstrap command; never put admin credentials in development seeds. Fail if a production seed command is invoked.

## 3. API contract

All successful JSON responses use predictable resource shapes; list routes return `{ data, page, pageSize, total }`. Errors use `{ error: { code, message, details? } }`, never expose stack traces, SQL, password hashes, provider tokens, or internal file paths.

| Method and path | Access | Request / behavior |
|---|---|---|
| `POST /api/auth/register` | Public | `{name,email,password,role,phone,locationRegion}`; validate, hash, create user, issue access JWT |
| `POST /api/auth/login` | Public | `{email,password}`; generic invalid-credentials response |
| `GET /api/auth/me` | Authenticated | Return safe profile fields |
| `POST /api/diagnoses` | Farmer | Multipart `image`; validate image; upload and run diagnostic; persist result |
| `GET /api/diagnoses` | Farmer | Paginated caller-owned history |
| `GET /api/diagnoses/:id` | Owner farmer or expert assigned through consultation | Return diagnosis details |
| `GET /api/products` | Public | Search/category/vendor filters, pagination, only in-stock catalog items |
| `POST /api/products` | Agrovet | Create a product with validated values |
| `PATCH /api/products/:id` | Owning agrovet | Update own product; never permit vendor reassignment |
| `GET /api/agrovets/nearby?region=...` | Public/authenticated | Match normalized region; bounded and paginated |
| `POST /api/orders` | Farmer | `{vendorId,items:[{productId,quantity}]}`; server computes prices and totals |

Authentication middleware verifies signature, issuer, audience, expiry, and allowed algorithm; it does not trust arbitrary JWT claims or a client-provided role:

```ts
import type { RequestHandler } from "express";
import jwt from "jsonwebtoken";
import { AppError } from "../utils/app-error";
import type { UserRole } from "../types/api-types";
import { env } from "../config/env";

const roles: ReadonlySet<string> = new Set(["farmer", "agrovet", "expert", "admin"]);

function isUserRole(value: unknown): value is UserRole {
  return typeof value === "string" && roles.has(value);
}

export const authenticate: RequestHandler = (req, _res, next) => {
  const [scheme, token] = (req.header("authorization") ?? "").split(" ");
  if (scheme !== "Bearer" || !token) {
    return next(new AppError(401, "UNAUTHENTICATED", "Sign in is required"));
  }

  try {
    const payload = jwt.verify(token, env.JWT_SECRET, {
      algorithms: ["HS256"],
      issuer: env.JWT_ISSUER,
      audience: env.JWT_AUDIENCE,
    });
    if (
      typeof payload === "string" ||
      typeof payload.sub !== "string" ||
      !isUserRole(payload.role)
    ) {
      throw new AppError(401, "INVALID_TOKEN", "The access token is invalid");
    }
    req.auth = { userId: payload.sub, role: payload.role };
    return next();
  } catch (error) {
    return next(
      error instanceof AppError
        ? error
        : new AppError(401, "INVALID_TOKEN", "The access token is invalid"),
    );
  }
};

export const requireRole =
  (...allowed: UserRole[]): RequestHandler =>
  (req, _res, next) => {
    if (!req.auth) {
      return next(new AppError(401, "UNAUTHENTICATED", "Sign in is required"));
    }
    if (!allowed.includes(req.auth.role)) {
      return next(new AppError(403, "FORBIDDEN", "You cannot perform this action"));
    }
    return next();
  };
```

If refresh tokens are added, store only hashes, rotate them, revoke on logout/password change, and use secure `HttpOnly`, `Secure`, `SameSite` cookies with CSRF protection rather than long-lived browser local-storage credentials.

Validation middleware should parse `req.body`, `req.params`, and `req.query` with schemas and replace/use parsed values. Set Express JSON limits (for example 1 MB), multipart limits separately, and reject unknown fields where practical. Central error middleware maps `AppError`, Zod validation errors, PostgreSQL unique violations, and Multer limit errors to safe responses; unexpected errors are logged with request ID and returned as generic 500.

### Authentication service pattern

Registration accepts only allowed public roles (farmer and agrovet; expert accounts should be invited or administratively verified). Administrator accounts are created only by the explicit environment-configured bootstrap command. Never accept `admin`, `password_hash`, permissions, `verified`, or a vendor identity from public registration input.

```ts
import bcrypt from "bcrypt";
import jwt from "jsonwebtoken";
import { AppError } from "../../utils/app-error";
import { db } from "../../db/knex";
import { env } from "../../config/env";

type RegisterInput = {
  name: string;
  email: string;
  password: string;
  role: "farmer" | "agrovet";
  phone: string;
  locationRegion: string;
};

export async function register(input: RegisterInput) {
  const passwordHash = await bcrypt.hash(
    input.password,
    env.BCRYPT_ROUNDS,
  );
  try {
    const [user] = await db("users")
      .insert({
        name: input.name.trim(),
        email: input.email.trim().toLowerCase(),
        password_hash: passwordHash,
        role: input.role,
        phone: input.phone.trim(),
        location_region: input.locationRegion.trim(),
      })
      .returning([
        "id",
        "name",
        "email",
        "role",
        "phone",
        "location_region",
        "created_at",
      ]);
    return { user, accessToken: issueAccessToken(user.id, user.role) };
  } catch (error) {
    if (isUniqueViolation(error, "users_email_uq")) {
      throw new AppError(409, "EMAIL_IN_USE", "An account already uses this email");
    }
    throw error;
  }
}

export async function login(email: string, password: string) {
  const user = await db("users")
    .select("id", "name", "email", "role", "password_hash")
    .where({ email: email.trim().toLowerCase() })
    .first();
  const matches = user
    ? await bcrypt.compare(password, user.password_hash)
    : false;
  if (!user || !matches) {
    throw new AppError(401, "INVALID_CREDENTIALS", "Email or password is incorrect");
  }
  const { password_hash: _passwordHash, ...safeUser } = user;
  return { user: safeUser, accessToken: issueAccessToken(user.id, user.role) };
}

function issueAccessToken(userId: string, role: string): string {
  return jwt.sign({ role }, env.JWT_SECRET, {
    subject: userId,
    algorithm: "HS256",
    issuer: env.JWT_ISSUER,
    audience: env.JWT_AUDIENCE,
    expiresIn: env.JWT_ACCESS_TTL,
  });
}
```

`isUniqueViolation` should check PostgreSQL SQLSTATE `23505` and the named constraint, using a typed driver error guard. Do not return different messages for nonexistent users and wrong passwords.

### Diagnostic uploads and AI boundary

Use Multer memory storage only with a strict maximum size (for example 8 MB), one image per request, and an allowlist of JPEG/PNG/WebP. Validate actual file signatures/MIME, not only the extension or client `Content-Type`; reject SVG and animated or oversized files unless explicitly supported. Strip EXIF/location metadata where feasible. Do not store the raw image permanently unless retention/consent policy allows it.

The media service uploads using a server-side Cloudinary SDK client configured from environment secrets. Set an unpredictable public ID, a private/authenticated delivery mode where appropriate, a folder per environment, and resource-type restrictions. Save only the provider URL/public identifier required for controlled deletion; extend `diagnoses` with `image_public_id` if lifecycle cleanup is needed. Never accept a client-supplied `image_url` for a diagnosis.

Use a provider-neutral contract so model changes do not affect the API:

```ts
export type DiagnosticInput = {
  image: Buffer;
  contentType: "image/jpeg" | "image/png" | "image/webp";
  subject: "crop" | "livestock";
};

export type DiagnosticResult = {
  detectedDisease: string;
  confidenceScore: number; // 0 to 1
  severityLevel: "low" | "moderate" | "high" | "critical" | "unknown";
  treatmentRecommendations: string;
  preventiveMeasures: string;
  requiresExpertReview: boolean;
};

export interface DiagnosticProvider {
  diagnose(input: DiagnosticInput): Promise<DiagnosticResult>;
}
```

The adapter must apply a network timeout, bounded retries only for transient provider failures, response-schema validation, and provider-specific rate limits. A low-confidence or out-of-distribution response becomes `unknown`/expert review, not a fabricated treatment. Store the provider/model version and an `ai_status`/job record in a later migration if asynchronous processing is enabled. Present output as decision support, not a definitive diagnosis; provide an expert escalation path and emergency guidance appropriate to the domain.

Request flow:

1. Authenticate farmer, validate upload, and verify the account is active.
2. Upload media to controlled storage.
3. Call the diagnostic adapter with timeout and strict output parsing.
4. Insert diagnosis only after a valid result.
5. If DB persistence fails after upload, attempt media cleanup and log cleanup failure; return an error, not a successful-looking response.
6. Return `201` with diagnosis ID, confidence, severity, recommendations, and review flag.

If AI latency/availability makes synchronous requests unsuitable, store a queued job and return `202 { diagnosisId, status: "processing" }`; add `GET /api/diagnoses/:id` polling or server-sent events. Do not return 202 unless the job is durably recorded.

In the real service, distinguish provider errors, persistence errors, and cleanup errors: log cleanup failures with request ID while preserving the original error; do not let a cleanup failure hide the primary failure. The content-type union is safe only after the upload middleware has performed signature validation.

Product creation accepts no vendor ID from the request; use `req.auth.userId`. Product listing uses parameterized Knex filters, a maximum page size (for example 50), stable ordering, and never interpolates raw SQL from search or sorting input. Nearby matching by region is a simple exact normalized-region filter; true geographic radius search requires adding coordinates and PostGIS/geospatial indexes rather than pretending region matching is distance-based.

### Order transaction: price integrity and stock concurrency

Input: `{ vendorId, items: [{ productId, quantity }] }`. Reject empty lines, duplicate IDs (or normalize by summing), invalid quantity, and carts with products from more than one vendor. Within one PostgreSQL transaction:

1. Select all requested products constrained to the supplied `vendor_id`, using `FOR UPDATE`.
2. Confirm every product exists, has sufficient stock, and is active/listable.
3. Recalculate total from current database prices using decimal-safe arithmetic (never JavaScript floating point for money). A robust implementation can use integer minor units after validating two decimal places or a decimal library.
4. Insert order with server-calculated total and `pending` status.
5. Insert order items with each current price snapshot.
6. Decrement stock with a guarded update (`stock_quantity >= requested`) and verify affected row count.
7. Commit; any failure rolls back all inserts and stock changes.

Idempotency keys are recommended for order creation to protect mobile retries. Persist `(farmer_id, idempotency_key)` under a unique constraint in a follow-up migration and return the original order on a safe repeat. Payment integration must add explicit payment states and webhook verification; do not mark an order paid because the browser says payment succeeded.

### Consultation scheduling

Use UTC timestamps, require scheduled time in the future, and verify the expert exists and has role `expert`. If linked, verify the diagnosis exists and belongs to the requesting farmer. For an MVP with fixed appointment slots, add an `expert_availability` table and enforce slot uniqueness/overlap in a transaction. A simple overlap check without a database lock is race-prone. At minimum, prevent duplicate expert bookings using a database exclusion constraint for a defined duration/slot model (PostgreSQL range + `btree_gist`) or lock the expert/slot row in a transaction. Status transitions should be explicit: pending → completed/cancelled; completed is terminal. Record who changed status and when in an audit table for production.

### Error middleware and application setup

Register middleware in this order: request ID and access logging; security headers; exact CORS allowlist; rate limiting; JSON parser with size limit; routes; not-found handler; centralized error handler. Error middleware logs unexpected exceptions and returns `{error:{code:"INTERNAL_ERROR",message:"An unexpected error occurred"}}` with HTTP 500. Return 400 for validation, 401 missing/invalid auth, 403 role/ownership denial, 404 missing resource, 409 unique/stock/scheduling conflict, 413 payload limit, and 429 throttling. Keep error details safe and useful for validation clients.

### Authentication, route protection, and navigation

Use an `AuthProvider` for the current user/session and a single API client for bearer-token handling and normalized errors. Keep access tokens in memory where practical; a reload-friendly refresh-token design should use `HttpOnly` cookies and CSRF defenses. Do not put long-lived bearer tokens in local storage. On 401, clear the session and redirect to login; on 403, show an access-denied state.

```tsx
type ProtectedRouteProps = {
  children: React.ReactNode;
  roles?: UserRole[];
};

export function ProtectedRoute({ children, roles }: ProtectedRouteProps) {
  const { user, isLoading } = useAuth();
  const location = useLocation();
  if (isLoading) return <PageLoading />;
  if (!user) {
    return <Navigate to="/login" replace state={{ from: location }} />;
  }
  if (roles && !roles.includes(user.role)) {
    return <Navigate to="/forbidden" replace />;
  }
  return children;
}
```

Frontend role checks are UX only; every API endpoint independently enforces authentication, role, and ownership. Navbar links are derived from role-to-link configuration, not scattered role conditionals. All form controls need labels, keyboard access, visible focus, and meaningful error messages.

### Diagnosis upload and timeline behavior

`ImageCaptureUpload` accepts camera capture on supported mobile browsers (`capture="environment"`) plus a normal file picker. Preview with an object URL and revoke it on replacement/unmount. Show selected file name/size, allow removal, and submit `FormData` without manually setting the multipart boundary. Resize large images client-side only as an optimization; server-side validation remains authoritative. Disable duplicate submits, expose progress/loading, handle offline/timeouts/retry, and preserve the selected image for a deliberate retry.

### Marketplace, cart, and checkout

Use TanStack Query for catalog and server state (cache keys include filters and page); use a small reducer/context or a lightweight store for ephemeral cart state. Persisting a cart locally is optional and must not persist payment credentials. Each cart line stores only product ID and quantity; refresh product price/stock before checkout. Group by vendor and prevent one order from crossing vendors. Show the server-calculated final total from the created order, not the client estimate.

Filters should be URL-backed for shareability and refresh recovery: query text, category, region/vendor, page. Debounce search, cancel stale requests, use page size around 20, lazy-load below-the-fold images, and use responsive cards with a clear stock state. Checkout submits the vendor ID and product IDs/quantities; server is authoritative for prices, totals, inventory, and eligibility.

### Expert schedule

The consultation page loads experts and available slots from API endpoints; booking posts an ISO UTC timestamp. Render local timezone explicitly and confirm it to the user before submit. Distinguish loading, no slots, conflict (409 with reload action), and server error. Farmers see their appointments; experts see only assigned appointments. Never expose another farmer’s diagnosis/notes in expert search results. Calendar controls must also have an accessible list view for screen readers and low-end/mobile devices.

## 5. Reliability, privacy, and production operations

* **Transport and secrets:** TLS everywhere; rotate secrets; use a secret manager; limit Cloudinary/API credentials to required operations.
* **Passwords:** bcrypt with calibrated work factor, minimum password policy, generic login errors, rate limits, and security-event logging without credentials.
* **Data access:** parameterized queries, ownership checks on every record read/write, least-privilege DB account, database backups with tested restore procedures.
* **Uploads:** limits on bytes/dimensions, MIME and magic-byte checks, malware scanning where risk warrants, private media, signed access, retention/deletion policy, no arbitrary remote URL fetches.
* **AI safety:** validate output, surface uncertainty, human escalation, model/version auditability, drift monitoring, and no claim that AI replaces professional advice.
* **Abuse controls:** request rate limits, pagination caps, payload bounds, CORS allowlist, CSRF protections for cookie auth, and audit log for privileged changes.
* **Observability:** structured logs with request ID, metrics for latency/error rate/AI timeout/queue depth, traces across API/DB/provider calls, health and readiness endpoints. Never log tokens, passwords, full uploaded images, or sensitive consultation contents.
* **Resilience:** request timeouts, DB pool sizing, provider circuit breaking, bounded retries, explicit degraded states, and idempotency for order/booking submissions.
* **Database evolution:** forward-only production migration discipline, backups before risky changes, index creation strategy appropriate to table size, and backward-compatible deploy sequencing.
* **Accessibility/localization:** WCAG-oriented semantics, keyboard navigation, readable contrast, text labels for icons, locale-aware date/currency formatting, translation-ready strings, and region-appropriate units.
* **Low bandwidth:** compressed responsive images, lazy loading, cache static assets, code-split dashboards, small JSON payloads, avoid autoplay/video, and offer clear retry/connection states. Consider a service worker only with explicit stale-data and logout/cache policies.

## 6. Verification checklist

### API and database

1. Fresh PostgreSQL database migrates up and down cleanly; migration constraints reject invalid roles, severity, confidence, negative price/stock, zero quantity, and invalid foreign keys.
2. Registration normalizes email, hashes passwords, does not permit expert self-registration, and never returns a hash.
3. Login returns the same error for unknown email and incorrect password; JWT rejects wrong issuer/audience/algorithm/expiry.
4. Every role-denied route returns 403; anonymous protected routes return 401; users cannot read or mutate another user’s data by changing IDs.
5. Diagnosis upload rejects invalid signature, MIME, size, missing image, AI malformed response, and provider timeout; successful diagnosis is persisted and associated with the authenticated farmer.
6. Product and nearby lists are bounded, parameterized, and stable under pagination.
7. Concurrent orders cannot oversell inventory; totals and item prices come from DB values; mixed-vendor and repeated requests are handled deterministically.
8. Consultation rejects past appointments, wrong-role experts, foreign diagnoses, invalid state changes, and concurrent booking conflicts.
9. API tests assert error response shape, status codes, and no sensitive data leakage.

### Web

1. Mobile layout works at narrow widths and slow network settings; upload preview, validation, loading, retry, success, and failure states are tested.
2. Role navigation and protected route behavior cover loading, unauthenticated, wrong-role, and allowed states.
3. Cart handles stock/price changes, vendor separation, duplicate clicks, and checkout failures.
4. Consultation calendar/list confirms timezone and recovers from conflict.
5. Keyboard-only navigation, focus handling in drawer/dialog, labels, contrast, and screen-reader names are checked.
